02

一次「AI 精读」的完整数据流

这条链路是整个应用最核心的一条：AI 的产出永远先回到 Markdown，再由索引跟着更新。 注意「写回前重读磁盘」那一步 —— 它保证 AI 跑的一分钟里你在别处改的字不会被覆盖。 每一次模型调用还会记一笔账（模型 / 耗时 / token / 重试次数 / prompt 指纹）， 随运行档案落盘 —— 失败的调用同样计入，因为它们一样计费。

AI 真正产出的那几节
—— 不会覆盖你手改的内容 V->>D: 更新索引（search_blob 等） T-->>R: 进度与结果 R-->>U: 界面刷新，可复制 / 导出
结构大纲（离线可读） 
你点「AI 精读」
  → 渲染层发 ai:analyze
  → tasks.ts 入队（顶部任务胶囊，可取消）
  → ai-service 读 papers/*.md 的章节 + .papervault/texts/ 的原文
  → 按维度（lens）拆成多次模型调用，每个 lens 独立 prompt / 采样参数 / 解析
  → llm.ts 请求模型（Key 只存在本机设置里，不经过任何服务器）
  → 结果写回 Markdown：**写前重读磁盘，只合并 AI 真正产出的那几节**
  → db.ts 跟着更新索引（标题、分类、search_blob、关系……）
  → 队列回报进度，界面刷新

同样的形状还有：实验画像、写作手法、方法流程图、AI 标重点、段落改写、找关系、
想法生成、组合分析、综述 —— 都是「读 Markdown → 多次调用 → 写回 Markdown → 更新索引」。

知识库目录：你的数据实际长这样

这是应用之外、用任何编辑器都能改的普通文件夹。删掉 .papervault/ 只是丢索引， 正文一个字都不会少 —— 重新打开应用会自己重建。

06

七条设计原则（都带着「为什么」）

这些不是口号，每一条都写在代码注释里，是遇到具体问题时的取舍依据。

Markdown 是唯一事实来源

正文只存在 papers/*.md，索引随时可从它重建。

为什么：这样你可以用 iCloud / git 同步，也能用任何编辑器改；应用坏了不丢笔记。

索引进 Markdown，状态进索引

AI 产出的正文写回 Markdown；搜索、图谱、阅读位置这类只进索引。

为什么：笔记要可迁移，而阅读位置这类丢了无所谓的数据不该污染 frontmatter。

AI 只提议，人做决定

找关系产出的是「待确认提议」，采纳后才进你的关系图。

为什么：关系图的价值在于它是你判断过的；AI 自动连线会让它变成噪音。

AI 拆成独立 agent

11 个 agent 各自持有 prompt、采样参数、解析与错误处理。

为什么：某一节失败可以单独重跑，不用整篇重来；改一个不影响其它的。

渲染层碰不到磁盘

所有文件与数据库操作都在主进程，经 57 个频道白名单通过。

为什么：界面层出问题也动不了你的笔记；路径还要再经 resolveInside 校验，防止越出知识库。

写回前重读磁盘

AI 收尾时重新读一遍文件，只合并它真正产出的那几节。

为什么：一次精读要跑一两分钟，这期间你很可能在别的章节打字，整份覆盖会把它们抹掉。

每次 AI 调用都留痕

模型、耗时、token、重试次数、system prompt 指纹，随该次运行的档案落进索引。

为什么：改 prompt / 换模型之后，「是不是真的变好了」得有据可依。失败的调用也记 —— 它们一样计费。
